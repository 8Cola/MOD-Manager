# 启停性能优化（2026-10-11）

目标：保留现有后缀启停、安全检查、可恢复日志和失败回滚，减少用户等待。

已完成：

- 启停前后只核对目标 MOD；全库状态仍通过目录监控和后台核对更新。
- 返回已经核对的目标 MOD 数据，开关不用等待全库快照；成功后不立即再排一次全库刷新，避免阻塞下一次点击。意外中断仍触发后台核对。
- 批量启停使用一个请求，后台逐项操作并发出带操作 ID 的进度和结果，失败项不会显示为成功。
- 检测游戏运行时仅收集进程名称和 EXE 路径，仍在每个 MOD 操作前重新检查，避免整批复用过期的运行状态。
- 文件夹成员清单按规范化路径查找；操作前身份和授权检查、操作后身份核对仍保留。恢复路径沿用原有严格核对。
- 整体结构、成员独占和路径范围仍全库验证；一次改名／文件夹启停的文件系统检查只针对实际操作的 MOD。完整导入、启动等验证不缩小范围。
- 监控注册只读取目录配置，不再每 3 秒生成全库磁盘快照。监控的事件、防抖、目录指纹和丢失事件补偿保留。前端兜底快照由每 3 秒改为每 15 秒，正常变化仍由监控主动通知。
- SQLite 仍使用 WAL 与 synchronous=FULL；恢复日志和关键管理信息仍逐项落盘，没有通过延后保存来缩短等待。

## 实际程序验证

`scripts/qa-toggle-speed.cjs` 使用真实 Windows WebView、原生文件操作及独立测试目录，没有修改真实 Steam MOD。最终一轮窗口点击到完成的测量：单文件 121 ms，40 文件夹 410 ms，批量 6 项 1455 ms。时间包含界面及自动化点击开销；批量包含一个冲突项，不能直接与后端全成功场景相除比较。

6 组流程通过：单文件、文件夹、关闭后添加新文件的混合状态、批量逐项进度与部分失败、修复冲突后重试、重启状态恢复。系统监控确实自动发现新文件，新文件没有被悄悄加后缀。

Rust 回归：96 项通过，另一个耗时探针标记为忽略并单独运行通过；包含文件占用回滚、目标冲突、符号链接／目录联接、游戏运行阻止、崩溃恢复、原图持久化和备份恢复。新增测试验证目标核对不会遍历无关文件夹状态、完整快照仍能发现无关变化，以及逐项进度与部分失败的准确性。

运行报告保存在 `output/toggle-speed-qa.json`。性能仍受实际文件数量、磁盘、文件占用、安全软件和后台扫描影响，不保证所有用户都达到以上时间。
